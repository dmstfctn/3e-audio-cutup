# Handover

For how the game works, read `README.md`, the comments at the top of `build/javascript/main.js`, which describe the step kinds, and the comments in `build/config/story.yaml`, whose `sequence` sets the order. `main.js` is split into sections marked `// ---------- name ----------`. The README's prototype sections describe `prototype/`, and `build/` has moved on from them.

## Working with this user

- The user works in small steps: they make a request, you make the change, and they check it. Several small requests often come in one message, as a list. Do them all, then report in one short list.
- Keep replies short: what changed, where, and what was checked. Don't recap the whole session.
- When a request is ambiguous, pick the plainest reading, do it, and say in one line what you chose. If the user's wording would make a feature do almost nothing, say so and offer the alternatives (e.g. "play a clicked word unless the loop is playing": the loop always plays at the end, so they chose "always").
- Point out problems your change causes or makes worse (e.g. the header overflowing on phones), and offer a fix rather than quietly widening the change.
- They sometimes send a new request mid-turn. Fold it into the current work.
- Commit only when asked. Commit on `main`, stage only the files involved, and end the message with the co-author line. The message is a short title and a few `-` lines.
- This file is tracked. When a change makes something here wrong, update it in the same commit.
- Files the user adds (e.g. audio in `build/audio/`) may be untracked. Leave them out of commits unless the game now depends on them, and say which files you included.
- `build/config/games.yaml` sometimes has uncommitted edits of the user's own. Check `git diff` before committing, and leave theirs out.
- The user's words for things: **the end** is the `write` step, **narrative moments** are the `page` steps, **the tray** is `#palette`. The **intro example** (the old silent first stage) is gone. Its line's words (`first` in `story.yaml`) are still in the tray at the end, but the lines start empty.
- The user writes story changes as text with `[button]`s and `->` instructions. `page` text in `story.yaml` uses the same `[button]` notation.
- Keep code comments short and plain, explaining why rather than what. Match the density of the code around them. When a change makes a comment in the code or a config file's comments wrong, update it.

## Checking changes

- **Syntax:** `node --check build/javascript/main.js` (and `minigames.js`).
- **Headless:** install `puppeteer-core` into your scratchpad (`npm i puppeteer-core`) and use `executablePath: '/Applications/Google Chrome.app/Contents/MacOS/Google Chrome'`. Serve `build/` on a spare port (`python3 -m http.server 8765`) and kill it afterwards. Check layout changes at 1280×800, at 3840×2160 (to see the scaling; `deviceScaleFactor: 0.5` keeps the screenshot small) and at phone size (390×844, `isMobile: true, hasTouch: true`), and read the screenshots. For audio, add `--autoplay-policy=no-user-gesture-required` and inspect state (`live.size`, `nextTime`, `paused`, `trackOn`) instead of listening.
- **Wait for load** with `lineEls.length && ($('#palette').children.length || $('#screen-go').textContent !== 'loading…')`. On a page, `#screen-go` gets its text; at the end the tray is built instead (and `#screen-go` stays at "loading…").
- **Jump to a step** from the console with `skip('find')` (a game), `skip('write')` (the end) or `skip(3)` (a step of the sequence). The games before it count as won in full. `skip()` bypasses `enter()`, so `skip('write')` doesn't fill line 1's opening pauses and yeah. Or set `localStorage.cutup` before a reload, e.g. `{ phase: 'write', at: 10, task: 3, start: ['pages'], results: {}, lines: [[], []], last: null, trackOn: {} }`. `phase` must match the kind of step `at` in the sequence, or a new game starts. Top-level `let`s (`GAMES`, `SEQUENCE`, `at`…) can be read and set from `page.evaluate`, e.g. `GAMES.find.seconds = 0.3` to rush the games. To give every word won, after load: `for (const key of GAME_ORDER) results[key] = { points: 0, total: 0, words: [...new Set(GAMES[key].items.flatMap(i => i.rewards))], tracks: [] }; save();`, then reload. Put track names such as `'metro'` in a result's `tracks` to unlock them.
- **The morph** (the strip growing into the tray) only runs going from the last page into `write`. To test it, start on that page (`{ phase: 'page', at: 9, … }`) with results filled in, click through `#screen-go` (waiting for each button: a click before it shows is ignored), and take screenshots a few hundred ms apart.
- **Pair-it by script:** dispatch `pointerdown` (with `clientX`, `clientY`, `button: 0`) on both `.mg-cell[data-pair="k"]` once `.mg-pairs` is visible and its images have their `src`.
- Headless can't show touch or momentum-scroll problems. Ask the user to try touch changes on their phone.
- **Versions:** `index.html` loads the CSS and JS with `?v=N`. Bump N on all four in a commit that changes any of them, or browsers (the user tests in a Firefox private window) keep the old files.
- There's no build step and no test suite. `build/` loads nothing from outside itself, so no CDN libraries.

## House style

Big screens: sizes are in `--u` (`style.css`), which is 1px up to a 2560 × 1440 window and past it grows with the smaller of width / 2560 and height / 1440, so a bigger window shows the 1440p layout scaled up. Write new sizes as `calc(N * var(--u))` (or in em); `UNIT()` in `main.js` is the same for px in JS (`BURST`, `JITTER`). Phones never reach it. The games' photos fill the room under the prompt at any size: caption match's three up to a third of its width each, pair it's grid as high as the room. Caption match's photos are each as big as fits in a 4:3 box, their buttons the photo's own size (from `--r`, set on load) so the outline hugs the photo, and they sit `--gap` apart, centred together: 64px at 2560 × 1440, scaling with the window below it too (`min(2.5vw, 4.444vh)`, not `--u`); 10px stacked on phones.

Times, black 1px borders and square corners. Green `#00ff00` means right and red `#ff0000` means wrong, in the games as `--ok` and `--bad` (`minigames.css`), set per play (`feedback()` in `minigames.js`, from `data.ok` / `data.bad`, per round in caption match) from `colours.json`'s `success` and `fail`, resolved by `coloursOf` in `planRun`. They're set only in its defaults now, as `#00ff00` and `#ff0000` (the per-photo ones were cleared: the user wants plain green and red everywhere), though a photo or game could still override them. They colour shapes found, a caption-match or pair-it photo's border, and a miss's ring. A pair-it photo picked, before its pair, has a black outline. An older top-level `feedback` in the file becomes the defaults' when the picker loads it. Everything is Times New Roman MT Condensed (`--hand`, from `build/fonts/times-new-roman-mt-condensed-…woff2`, its bold from `times-new-roman-mt-bold-condensed-…woff2`, both preloaded in `index.html`) except, on desktop, the lines' on buttons and the − / + under them (Arial). The on button's letters stand on the line's bottom edge (`line-height: 1`, nudged down 1px). The words (the tray, the lines, the strip, a word won flying, submit's lines) use `--hand` too. `markCut()` runs again when a font finishes loading. The user tried Just Another Hand before and switched it back; its `@font-face` is commented out in `style.css` and the font is still in `build/fonts/`. The strip's words are bold 20px. `TILT` is 0, so nothing leans, but the tilt code is still there: at a non-zero `TILT`, a word's text leans up to ±`TILT`°, and the boxes in the tray and the lines lean too, separately from their text. The tilts are kept per word id in `tilts.tray` / `tilts.lines`, so redrawing a line doesn't shuffle them, and dealt again when a word is clicked into the lines or dropped (the tray word clicked or dragged gets a new one too). Two copies of one recording in the lines lean alike. The strip's and submit's words get a new tilt each time they're made. Play/pause is a standard play or pause icon (inline SVG); submit is plain bold text. The header only shows at the end: play/pause at the left, the track toggles centred (on phones, left after play/pause), and submit ("submit your lines") at the right. On phones it just fits five toggles at 390 px, with submit at 14px. There's no points counter: each +1 (`#00ff00` with a black outline, unless `colours.json` says otherwise) bursts out from the click (240–480 px, `BURST`) in any direction except down-right, where the words go, and fades. Find them all flies 10 per shape (`points: 10`). A game's timer bar runs along the very top of the screen, black, flashing `#ff0000` and black by turns (0.3 s each) for the last 20% of the time or 2 s, whichever is longer (`LOW_FRAC`, `LOW_SECS` in `minigames.js`). Word blocks (tray, lines) have black text and border (none in the lines), coloured by bin, from the scheme `use:` names in `config/word-colours.yaml` (`loadWordColours()` sets `--bin-noun` etc.; `style.css` falls back to `original`). `original` is the colours from `c9ccd56`, 25% darker: nouns `#bf5c5c`, verbs `#57a16b`, adjectives and describers `#5f89bf`, yeahs `#bfa238`, pronouns and glue `#737373`, pauses `#bfbfbf`. The other schemes are ones the user tried on 2026-09-30; other bins stay black with `#ccc` text. Each line's on button comes after it, the word "on" in 12px uppercase Arial (`--mute-w`, 34px wide), greyed out while the line's off, standing on the line (bottom-aligned); a gutter as wide on the left keeps the lines centred. A line off fades. The lines run 8px from the page's edges. On phones (≤ 640px) there are no on buttons and no gutter, the lines are drawn 2px from the edges, and `#active` under them has a square per line (filled with `--ink` when on, faded to .3 when off) with − / + right after it, moving right as lines are added; squares, − and + are all about 6px apart (measured on the glyphs' ink: + has more space on its left, hence its -4px margin). Also on phones, `#now-word` at the top shows the word being said (set in `drawPlayhead()`), in submit's size, its space always kept (`flex: none`); the lines and their controls are centred in the space between it and the tray, rising as lines are added until they're 16px under it, then running on below. Words in the lines are the tray's size (12px on phones, and on phones on their side: `(orientation: landscape) and (max-height: 500px)`, which otherwise get the desktop layout); on phones word blocks are 24px high, as are the lines, with the lines' thick end ticks swapped for thin grey ones at the very ends and the words' room 2px wider each side. A word in a line too short for its text is squeezed across (`scale` on its span, from the left) until it fits (`markCut()`, class `.cut`); a pause shows the `~`s that fit; the mouse over it, or a long press (`HOLD_MS`), shows it at the tray's size above the pointer (`peekable()`), and letting go of a long press doesn't remove it. The playhead draws over the words. `touch-action: manipulation` everywhere stops double-tap zoom. Nothing on the page can be selected (`user-select: none` on `html`), as quick taps on iOS selected words. In the strip, words won have no block, each in a random one of the strip colours of the photo being played: they all re-tint (fading, 0.9 s) as each play starts, and each caption-match round (`tintStrip()`, via `data.onRound`); pair it uses the game's. Strip colours lighter than `STRIP_MAX_L` (70, CIE L*) are dropped from `colours.json`'s lists as it loads (`loadColours()`), as they were lost over the games' backdrop; a list left empty falls back as usual. (The user tried a white glow and black words first, and kept the colours.) The colours are kept in `results[key].hues`, so a reload keeps them; they become blocks flying into the tray at the end. The strip has no top border. Find them all's count follows the prompt, "(n/N)". A word won grows from nothing at the click over 0.2 s to 12× size as outlined text (6px on screen) cycling through its photo's flash colours (smaller if it won't fit, and nudged in from the screen's edges), holds there for 0.5 s, then shrinks into its place in the strip, where it takes its colour. On a dark page the strip turns black and its words go grey; see `body.dark` in `style.css`. Writing (the end, and submit's screen) is all `#ccc` on black (`body.writing`), as is a dark page's text and its strip; the lines' ticks, bottom border and drop marker take their colour from `--ink`. Buttons on the narrative screens, and retry / next task on a game's points card, are underlined story text. Rows a button reveals together come in 350 ms apart (`LINE_GAP`), and the next button 600 ms after the last of them (`BUTTON_GAP`). The tray is full width with a border on top only: one panel, the pauses first, then words A–Z, centred, scrolling past 66% of the screen (40% on phones, upright or on their side), with fades about a word high at its bottom while there's more to scroll to and at its top once scrolled (`fades()`, which also fades the lines under the header and over the tray when `#game` scrolls).

## State of the game

- The order is `sequence` in `story.yaml`: `page` (light or dark, text in `[button]` notation), `try` (a game with no timer until its first win, winning nothing; `seconds: null` in minigames.js; its own `prompt:` replaces games.yaml's, `{caption}` included), `games` (one step at most; after each game an `X / Y words` card, words won out of those the run could win, with one retry per game (`retried`) and next task, the last button being the step's `last-button`), and `write`. Any step can `play` (unlock and switch on), `unlock` (off) or `stop` (switch off) tracks. The metro plays from the games until the dark page. `write` plays the beat. The drone is in `games.yaml` but nothing unlocks it now (`write`'s `unlock: [drone]` is commented out).
- `restore()` rejects a save whose `phase` doesn't match the kind of step at `at`, so editing the sequence can reset saves. That's fine.
- Pair-it tries leave out pairs matched in earlier tries (`tried`, saved); the timed game has them all.
- The header only shows at the end. The strip shows from the games until the end.
- The end has 2 to 8 lines, added or removed one at a time by + (under the on buttons) and, with more than 2, − just left of it. Each keeps its place when hidden, so + never moves. Each line has an on button after it (`lineOff`, shown by `aria-pressed`): a line off is skipped by the loop and submit, and clicked words pass it by, but a word can still be dragged into it. The ≡ handles that moved lines are commented out in `buildLines()` (`startRowDrag` and `.handle` remain).
- The end's line 1 starts as a 2-beat pause, a 1-beat pause and the first yeah the tray offers, if every line is empty on entering `write` (in `enter()`).
- The tray offers at most `TAKES` (1) recordings of each word, so no duplicates, picked at random once per game (`picks`, saved) from those `config/clips.json` leaves on, and at most `MAX_YEAHS` (5) yeahs in all, also picked once per game (`picks[' yeahs']`).
- `build/tools/clippicker.html` (served at `/tools/clippicker.html`) auditions every recording, trims its bounds and switches it off; it exports `clips.json`, which the user moves to `build/config/`. The game applies it in `applyClips()`; without it, every recording plays with `PAD` around its aligned bounds. `LONG_TAKE` is gone: the 0.9 s "it" is offered again until it's switched off in the picker. The picker keeps unexported edits in `localStorage`.
- `build/tools/colourpicker.html` shows every photo in `games.yaml` with two rows of colours (k-means in Lab, 3–16 per row; each swatch a real pixel, not a cluster's average): common, the colours covering the most of the photo, and vivid, from its saturated pixels only (chroma ≥ `VIVID_CHROMA`), weighted by chroma, each cluster's 90th-percentile-chroma pixel, near-duplicates (under `VIVID_APART`) dropped, and picks colours for the effects of a win on it: `points` (the +1s), `flash` (the word won's outline, cycled 0.1 s per colour), `strip` (the words in the strip), and `success` / `fail` (one colour each; see House style; when a file has none, the picker's defaults start as green and red, so an export always sets them), per photo and as defaults. It exports `colours.json` for `build/config/`, and imports one. The game reads it in `loadColours()`, and `coloursOf(key, photos)` resolves a win's lists: the game's (`games`), then the photo's own, then `default`, then `COLOURS` (the old green and six hues). Pair it is one card and one set of lists for the whole game, clustered from all 12 photos (1,000 pixels each), under `games` → `"pair-it"` (`WHOLE_GAMES` in the picker); the game's `coloursOf(key, photos)` checks `colours.games[key]` first. Older per-pair (`'A1.jpg + A2.jpg'`) and per-photo pair-it entries are dropped when the picker loads (`dropPairs()`), and the game ignores them; caption match uses the answer photo, so decoys only supply colours for the defaults. The flash is a CSS `@keyframes` made per list (`flashAnimation()`), because the Web Animations API doesn't animate `-webkit-text-stroke-color`.
- The games (tries included) and their points cards sit on a backdrop of the photos being played, blurred and paled (`setBackdrop()` in `main.js`, `#mg-backdrop` in `style.css`), running behind the strip too: one photo covers the screen, caption match's three are tiled in a row (stacked on phones), in the order shown, so none stands out, and pair it's 12 in a 4 × 3 mosaic (3 × 4 on phones). Each new set fades in over the last; the points card keeps the last game's. How pale is the white over it (`.4`), how soft its `blur(40px)`. **Hidden for now:** one line in `style.css` (`#mg-backdrop > div { display: none; }`) hides the photos, leaving the games on plain white; the code still runs, so deleting that line brings them back.
- Leaving a dark page, a black `.cover` fades out over `MORPH_MS` while the bars' CSS transitions run, and the words flying from the strip into the tray fade from grey to their colours (`morphTray`).
- Tracks are `.mp3` files in `build/audio/` (the `.wav` files are kept; `track-metronome-old.mp3` is the user's untracked backup), named `drone`, `metro`, `beat`, `strings` (`track-string2.mp3`; `track-string1.mp3` isn't used) and `all` in `games.yaml`, the toggles in that order. Each is 8 bars. At the end line i plays over bars 2i+1–2i+2, whichever lines are off (`TRACK_LINES` = 4, so line 5 is bars 1–2 again); before the end the loop runs through all 8. `track-drums.mp3` was replaced on 2026-09-29; checked: 13.371 s like the others (8 bars at 143.59), in phase with the old one and `all`. Tracks won in games arrive switched off. A toggle at the end fades its track (and, for `all`, the others) in or out over `TOGGLE_FADE` (1 s); other changes are near-instant. `all` mutes the others while it's on (`SOLO_TRACKS`), including the drone and strings. Pair it unlocks `beat`, find it `strings` (first thing found), find them all `all`; caption match unlocks nothing. A track unlocked in the games joins the loop off, with no toggle until the end.
- Rewards: in `games.yaml` each photo, pair or round lists its words as one list, any bins (the older lists by bin still load, their bins ignored). Find it gives one word per thing, set after it (`thing: word`, or `{ reward, prompt }`), the thing's own if none (no speed share); its photos' old lists are kept as `# was listed:` comments. Caption match gives only a round's first listed word. Pair it gives the pair's words. Find them all gives the first listed word at the first found (the thing's own, as listed now; with no list, the thing's own is the only one), then `FIND_ALL_EXTRA` (3) of the photo's others picked at random per run, at evenly spaced counts. Each of those is a verb, adjective (or describer) or noun with the odds in `EXTRA_ODDS` (40/40/20), by the word's real bin; a kind the photo has none left of drops out and the others' odds scale up, so with few verbs and adjectives listed per photo, nouns fill in (checked: 3.jpg comes out 57% adjective, 43% noun). Its count shows after the prompt, "find the fruits (1/45)".
- At time-up a game's prompt keeps its height (`g.say`), so the photo under it doesn't move.
- The recording loads from `words.mp3`, made from `words.wav` with `lame -V 2` (see the README). In Chrome it lines up with the WAV to the sample, because LAME's header lets the browser trim the encoder delay.
- Submit: "submit your lines" in the header plays the lines once on their own (`#show`), with [back to writing] and [submit your lines] under them, as underlined story text, and `submitted` from `story.yaml` under those (paragraphs at blank lines, `[text](url)` a link in a new tab, no url just text); `#show` scrolls if it doesn't fit. The second [submit your lines] does nothing yet. The user put a `* ` before the first paragraph in `story.yaml`; it shows as a literal asterisk (only links are supported), so ask what it's for if it comes up. Nothing is sent anywhere: the lines stay in the player's browser. The old [restart] button is gone (`restart()` remains, unused).
- Images on pages (see `story.yaml`'s comments): a row `![](story/x.jpg)` is an image from `build/images/`, up to 40% of the screen high (`40svh`), fading in like a row; a page with `image:` instead of `text:` is one image up to 60% high, shown whole with no border, moving on by its `button:` or, with none, a click on the image (`#screen-text.whole` / `.click`). The alt text is always empty. `preloadImages()` loads the images of the step shown and the next two. On phones only the width shrinks them; two images and text on one page nearly fill a 390×844 screen.
- Play/pause (and the space bar) stops the loop. It's not saved.
- The end doesn't scroll unless it has to: `#game` is fixed and scrolls only if the lines don't fit, and the tray scrolls when its words overflow (with every word in one panel, it usually does). On touch, a tray word drags straight away unless the tray scrolls, when it has to be held for `HOLD_MS` first. The page doesn't rubber-band (`overscroll-behavior: none`).
- The word won grows by its font size, not a transform, because iOS Safari pixellated the transform.
- Words won are not said, but each word flying to the strip plays `win.mp3` (`playUnlock`, which cuts off the one before), each point scored `click.mp3` (`playClick`), and each miss `click-wrong.mp3` (`playWrong`, on the `mg-miss` event `missAt()` in `minigames.js` dispatches, as do a wrong caption-match photo and pair it's picks and wrong pairs; rapid misses restart it). In a pair-it try it also plays on a match (`startTry()`). All at 0.6 volume, straight to the output (play/pause doesn't affect them). A clicked tray word is always said (`playWord`). It flies from the tray into its place in the line over `TAP_FLY_MS` (250 ms; `flyInto()`), a copy stretching to the line word's size, which shows once it lands. A word clicked out of a line flies back to its tray word the same way (`flyBack()`, in `BACK_FLY_MS`: 180 ms), fading on the way if that's scrolled out of view. A word dragged by a finger stays under it where it was picked up (`moveTouch()`).
- About 4.7 MB loads before [start] is enabled: `words.mp3` 3.2 MB, all four tracks 1.2 MB, the find/find-all shape `.svg`s 190 KB (mostly `12.svg`), the rest small. `click.mp3` and `win.mp3` load alongside but aren't waited for, so the first clicks may be silent. Photos load when their game starts; they're small JPGs now (7, 10, 13–18 were PNGs; `12og.jpg` is 12's full-size original, unused). Pair it's photos are deliberately blocky: each was shrunk to 60%, saved at JPEG quality 20, then enlarged back with nearest-neighbour (`magick A1.jpg -resize 60% -quality 20 jpg:- | magick - -filter point -resize WxH! -quality 90 …`); the originals are in `images/pair-it/original/`, unused. `12.svg` is still drawn at the original's size, which is fine: shapes scale by their viewBox.
- Added but not used yet: `audio/win-short.mp3`, `images/story/awake.jpg`, `video/teaser.mp4` (for the end).
